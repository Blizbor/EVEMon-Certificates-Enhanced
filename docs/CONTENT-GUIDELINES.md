# Content guidelines / Zasady tworzenia treści

## English

These rules apply to documentation and certificate changes in **EVEMon Certificates Enhanced**.

### Project role and scope

- Improve the readability of selected default EVEMon certificates. Do not turn the project into a general training plan, fit guide or fleet doctrine.
- Each certificate must answer a concrete capability question, such as T1 access, T2 access, specialization depth or support-skill quality.
- Keep broad pilot auditing in EVEMon Pilot Progression and activity-specific training in EvE Modular Skillplans.
- Modify only certificates that require clearer practical interpretation. Leave unrelated default certificates unchanged.

### Certificate design

- Define the practical meaning of every grade before choosing requirements.
- Keep an unlock separate from support depth when combining them would make the grade ambiguous.
- BASIC should represent a sensible entry point, not merely the first trainable skill.
- Every higher grade must correspond to a visible unlock, specialization threshold or measurable improvement.
- Do not require level V only for symmetry or completion. Its SP cost must have a clear practical justification.
- Do not hide a T2 gate inside a broad collection of unrelated support skills.
- State intentional shared thresholds explicitly when two adjacent grades use the same specialization level for a documented reason.

### Alpha and Omega clarity

- State when T2 access, specialization or another requirement is Omega-only.
- Explain what the certificate can still show for an Alpha pilot and where account limits prevent further progression.
- Distinguish an account restriction from an actual training gap.

### Documentation and maintenance

- Use current EVE skill names and verify dependencies against current EVEMon datafiles.
- Document which default certificate changes, why the default interpretation is insufficient and what each replacement grade means.
- Preserve identifiers and compatibility with the default datafile unless a documented migration requires a change.
- Keep the patch independent from EVEMon Pilot Progression so both projects can coexist.
- Do not use arrow symbols. Use lists or explicit wording for alternatives, prerequisites and ordered stages.
- Use neutral, factual language. Avoid first-person recommendations and speculative digressions about fits or doctrines.

## Polski

Poniższe zasady obowiązują w dokumentacji i zmianach certyfikatów projektu **EVEMon Certificates Enhanced**.

### Rola i zakres projektu

- Poprawiamy czytelność wybranych domyślnych certyfikatów EVEMona. Nie przekształcamy projektu w ogólny skillplan, poradnik fitowania ani doktrynę flotową.
- Każdy certyfikat musi odpowiadać na konkretne pytanie o możliwość pilota, na przykład dostęp do T1, dostęp do T2, głębokość specjalizacji albo jakość supportów.
- Szeroki audyt pilota pozostaje w EVEMon Pilot Progression, a trening zależny od aktywności w EvE Modular Skillplans.
- Zmieniamy tylko te certyfikaty, które wymagają czytelniejszej praktycznej interpretacji. Pozostałe domyślne certyfikaty pozostają bez zmian.

### Projektowanie certyfikatów

- Najpierw definiujemy praktyczne znaczenie każdego poziomu, a dopiero potem dobieramy wymagania.
- Oddzielamy unlock od głębokości supportów, jeżeli ich połączenie utrudniałoby interpretację poziomu.
- BASIC ma oznaczać sensowny punkt wejścia, a nie tylko pierwszy możliwy do wytrenowania skill.
- Każdy wyższy poziom musi odpowiadać widocznemu unlockowi, progowi specjalizacji albo mierzalnej poprawie.
- Nie wymagamy poziomu V wyłącznie dla symetrii albo kompletności. Jego koszt SP musi mieć jasne uzasadnienie praktyczne.
- Nie ukrywamy wymogu T2 w szerokim zbiorze niezwiązanych z nim supportów.
- Jeżeli dwa sąsiednie poziomy celowo używają tego samego poziomu specjalizacji, opisujemy wprost powód takiej decyzji.

### Czytelność dla Alpha i Omega

- Wskazujemy, kiedy dostęp do T2, specjalizacja albo inne wymaganie jest dostępne wyłącznie dla Omega.
- Wyjaśniamy, co certyfikat nadal pokazuje pilotowi Alpha oraz w którym miejscu limit konta zatrzymuje dalszą progresję.
- Rozróżniamy ograniczenie konta od rzeczywistej luki w wyszkoleniu.

### Dokumentacja i utrzymanie

- Używamy aktualnych nazw skilli EVE i weryfikujemy zależności w bieżących datafiles EVEMona.
- Dokumentujemy, który domyślny certyfikat jest zmieniany, dlaczego jego standardowa interpretacja jest niewystarczająca oraz co oznacza każdy poziom zamiennika.
- Zachowujemy identyfikatory i zgodność z domyślnym datafile, chyba że udokumentowana migracja wymaga zmiany.
- Patch pozostaje niezależny od EVEMon Pilot Progression, aby oba projekty mogły współistnieć.
- Nie stosujemy znaków strzałek. Alternatywy, wymagania i kolejne etapy opisujemy listami albo jednoznacznym tekstem.
- Stosujemy język neutralny i rzeczowy. Unikamy rekomendacji w pierwszej osobie oraz spekulacyjnych dygresji o fitach i doktrynach.
